## 1. 摘要

`codex-figure-acceptance` 是一个只读的视觉验收插件。它让 Codex 主代理枚举论文、报告和技术文档中的全部逻辑图位，针对每个图位派出一名固定为 `gpt-5.6-luna` 的视觉审计子代理，并生成可追溯的审计账本和可执行的修复交接。

产品不自动裁图、修图、修改 LaTeX 或重写图注。上游写作或制图工作流根据修复交接完成修改后，再运行本插件确认闭环。

## 2. 背景与问题

“PDF 成功编译”只说明构建链可用，不能说明图像可读、完整、与叙述一致。本项目的实际失败案例包括：

- 原论文 Figure 被裁断，左侧模型名、坐标轴、图例、底部图注或脚注缺失；
- 为解释图表而截入大段英文正文，真正的图反而不清晰；
- 委托人要求保留图注，或要求原始截图另配一张独立汉化图，但交付物未满足；
- 自绘图的标题、图例、坐标标签和正文相撞、遮挡、溢出或缺字；
- 原图是中文决策树，所谓“汉化重绘”却变成无关柱状图，形成图像错配与语义误导；
- 同一个素材在不同页面或不同裁剪框中的效果不同，却只抽样检查其中一处。

通用视觉检查没有提供“全量图位覆盖、用户要求继承、并行子代理、结构化修复交接、公开回归集”的完整闭环。本产品填补该空缺。

## 3. 愿景与价值

让任何 Codex 写作工作流都能在交付论文、报告、技术文档前，对全部图表执行可追溯的视觉验收；失败时交付可直接交给上游 Agent 或人工作者的修复说明，而不是模糊地说“图片有问题”。

## 4. 目标与发布门槛

### 4.1 产品目标

1. 每个已发现逻辑图位都有 `PASS`、`FAIL` 或 `NEEDS_HUMAN` 状态；未审计图位不得默认为通过。
2. 每名视觉审计子代理固定使用 `gpt-5.6-luna`，不得静默改用 Terra、Sol 或其他模型。
3. 每项结论可追溯到图位、页面或源文件、图像哈希、需求、模型、运行时间、证据定位和修复建议。
4. 公共回归集中所有阻断性缺陷均被识别；未覆盖图位永远不能产生整体 `PASS`。
5. 初始版本可安装、可复现、可贡献、可阅读，并具备中英双语产品说明。

### 4.2 发布门槛

- 图位覆盖率为 100%。
- 子代理模型锁定合规率为 100%。
- 所有账本通过 JSON Schema 与一致性校验。
- 公共阻断性 fixture 全部检出，且零例错误地输出整体 `PASS`。
- README 的本地图片、链接、命令和示例路径均可验证。
- 未提供真实 GitHub `owner/repository` 前，不推送、不发布，公开版本不得遗留占位符。

## 5. 非目标

- 不自动修图、重排 LaTeX、重写图注或修改被审计文档。
- 不替代事实核验、引用审计、版权判断或专业领域同行评审。
- 不从互联网自动抓取论文图片。
- 不承诺判断所有科学结论的真伪；只判断图像与用户意图、文档上下文是否一致。
- 不把用户私有图片上传、公开发布或提交到公共测试资产。

## 6. 用户、场景与工作流

### 6.1 用户角色

| 角色 | 需要解决的问题 |
| --- | --- |
| 报告作者 | 交付前检查每张图，避免裁断、遮挡、配错图和不可读文字。 |
| Agent 工作流作者 | 将验收置于写作/制图完成后；失败时将修复交接回传并重跑。 |
| 有特殊视觉要求的委托人 | 表达“必须含图注”“只用正式 Figure”“原图另配汉化图”“仅自绘图”等条件。 |
| 维护者/贡献者 | 添加可公开发布的缺陷 fixture，防止历史问题回归。 |

### 6.2 典型旅程

1. 用户指定 LaTeX、Markdown、PDF 或图片目录，并附带自然语言验收要求。
2. Main agent 发现图位，记录每个图位的源文件、页面、图注和资产哈希。
3. Main agent 将显式要求、可解释的上下文推断和默认规则写入已解析要求账本。
4. 每个图位分派一名 Luna 子代理；子代理查看完整上下文后返回严格 JSON 结论。
5. Main agent 验证结果、检查覆盖率并输出整体状态与修复交接。
6. 上游作者或 Agent 修复失败项，随后重新运行验收。

## 7. 用户故事与验收条件

### US-01：全量图位审计

作为报告作者，我希望插件逐一列出并审计所有图位，从而不遗漏重复引用或附录图。

**验收条件：** 图位清单数、任务数和终态数一致；任何未完成任务均使整体状态为 `NEEDS_HUMAN`。

### US-02：特殊图注要求

作为委托人，我希望明确“图注必须包含”，从而避免默认裁剪规则破坏交付标准。

**验收条件：** 该要求进入相关 Luna 任务和最终账本；缺少必要图注即为 `FAIL`。

### US-03：原图与独立汉化图

作为作者，我希望“原始截图 + 独立汉化图”被视为两项相关但不同的资产，从而不把篡改原图误当作合格翻译。

**验收条件：** 原图与自绘/汉化图分别标记角色、分别审计，并检查二者是否指向同一任务含义。

### US-04：修复交接

作为工作流作者，我希望获得具体修复交接，从而让上游 Agent 能定位应补回的标签、图注、裁剪范围或错误素材。

**验收条件：** 每个失败项提供位置、严重性、证据、违反的要求与建议修复动作。

### US-05：安全贡献

作为维护者，我希望新增缺陷样例不会暴露私有资料，从而可以安全地在 GitHub 上回归测试。

**验收条件：** 公共 fixture 只含手工重绘、自有或明确可再发布资产；CI 不依赖用户附件。

## 8. 功能需求

| ID | 需求 | 验收方式 |
| --- | --- | --- |
| FR-01 | 支持 LaTeX、Markdown、PDF 与图片目录，并以逻辑图位建档。 | 四类输入各有成功、部分成功和失败回归。 |
| FR-02 | 解析用户要求与上下文，生成可审计的要求账本。 | 特殊图注、原图/汉化图和冲突情形均有测试。 |
| FR-03 | 为每项审计提供页面、候选图、图注和源文件上下文。 | 子代理任务账本包含必要定位与证据。 |
| FR-04 | 一图位一 Luna 子代理，并发上限为 `min(30, 系统上限)`。 | 模拟调度与任务账本验证。 |
| FR-05 | 识别裁断、正文过量、图文错配、碰撞、遮挡、不可读、错位、重复与角色混淆。 | 公共 fixture 回归。 |
| FR-06 | 验证子代理 JSON、合并结果并执行覆盖率门禁。 | Schema 与门禁测试。 |
| FR-07 | 输出机器可读账本和人可读修复交接，且不修改输入。 | 文件系统只读测试。 |
| FR-08 | 提供可公开发布的手工重绘 fixture 与预期结论。 | CI 回归。 |
| FR-09 | 提供贡献规范，要求记录素材来源、许可、预期缺陷和断言。 | 文档审阅与样例 PR 模板。 |

## 9. 要求优先级与视觉判定

在不违反平台安全限制的前提下，要求优先级固定为：

1. 用户当轮明确要求；
2. 从当前任务上下文可解释地推断出的要求；
3. 模式预设；
4. 通用默认规则。

“必须截入图注”“原始截图额外配汉化图”等均不是全局默认条件；只有用户明确要求或上下文充分支持时才启用。冲突必须进入账本并返回 `NEEDS_HUMAN`，不得由子代理静默猜测。

默认错误分类包括：裁断、过度截取、文字碰撞、遮挡、溢出、低清晰度、缺字、标签/图例/坐标轴缺失、图文/图注不一致、原图与重绘角色混淆、重复/错位与“图片打架”。

## 10. 状态、严重性与交付物

- `PASS`：所有图位已审计，且不存在违反已解析要求的阻断性问题。
- `FAIL`：存在确认的视觉、语义或完整性缺陷。
- `NEEDS_HUMAN`：模型不可用、输出无效、证据不足、输入无法安全渲染或要求冲突。

每个发现标记为 `blocking` 或 `advisory`。任何 `blocking` 发现导致整体 `FAIL`；未覆盖任务或不确定性导致整体 `NEEDS_HUMAN`。

每次运行输出 Markdown 摘要、JSON 摘要、图位清单、任务账本、发现账本、需求账本、覆盖率账本与修复交接。

## 11. 隐私、安全与可靠性

- 插件不自动上传、公开或提交用户资产；公开 fixture 不得复制用户素材。
- 审计记录默认保存路径、哈希与证据定位，而不复制原始图片。
- LaTeX 渲染使用隔离构建目录并禁用 shell escape；无法安全渲染时 fail-closed。
- 子代理固定 Luna；同模型一次重试仍不能返回合格 JSON 时升级人工，不换模型。
- 原生 Codex 无法由插件替换宿主 system prompt。产品将版本化的审计指令原样注入每次子代理任务，并如实说明该边界。

## 12. 依赖、风险与开放事项

- PDF 页面渲染依赖 `pdftoppm`；PDF 图像对象发现依赖 `pdfimages`。缺失时产品保留可用的静态发现能力，但必须报告限制。
- LaTeX 构建依赖本地 XeLaTeX；渲染失败不应误报通过。
- 子代理能力和并发上限由用户的 Codex 环境决定；无法使用 Luna 时产品必须停止为人工复核。
- 公开 GitHub 远程、发布者姓名和联系地址尚未获得授权，不在初始仓库中伪造。
